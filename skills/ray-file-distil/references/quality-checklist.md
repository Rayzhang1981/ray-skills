## 完整性测试

选 3 个资料中明确讨论过的问题，用新 skill 分析，结果应与资料结论一致。

## 迁移测试

## 定向盲测（子代理只读产出，v1.16.0 新增）

> 把上一节的「完成判据」（换一个 agent 不读原文能否照做）从**口头判据**落成**可执行测试**。
> 判据管"够不够格"，本节管"怎么把它测出来"。

**五步做法**：

| 步 | 动作 | 要点 |
|----|------|------|
| 1 出题 | 从资料核心能力域出 **5 题**，每题对应一个核心模型；含 1-2 题考**边界/失效条件** | 别出"资料里明写的一段话"式记忆题 |
| 2 投喂 | 派**子代理**，只给它**产出 skill 目录**，明确**禁止读原文/原书/其他资料** | 任务书写死"只能用产出文件内信息作答，用外部知识补的要标出来" |
| 3 收答 | 子代理逐题作答，**答完单列「读后困惑」**（产出里没讲清、只能猜的点） | 困惑与答案**分开收集**，别混在正文里 |
| 4 判定 | 逐题核答案是否**全部落在产出文件内**；外部知识补全数 **M 应 = 0** | M>0 → 产出有空洞，回原文补 |
| 5 处置 | 每条困惑三选一：①真缺陷 → 补产出 ②原书本身盲区 → 标注"原书未展开"、**不编造** ③迁移 `references/` 的代价 → 在附页读法处声明 | 逐条裁定，**不许合并同类项** |

**⚠️ 铁律：子代理的读后困惑必须原样取回，禁止凭印象汇总（2026-09-11 实证）**

凭印象汇总得 **3 条**困惑，取回原始记录实为 **7 条**——**漏掉的 4 条里含 1 条真缺陷**
（第 488 行"随机性不成立时的三个根因"实为"**分布非正态**的三个根因"，原书 §3.4.7 只有这一份清单）。

**凭印象汇总 = 漏检通道**：印象只留"记得住的"，而真缺陷往往正是"当时没看懂、扫过去了"的那几条
——**越看不懂越记不住，越记不住越漏掉**，筛选方向恰好与需要相反。

**做法**：要求子代理**把困惑写成清单落盘**（或原样贴回消息），按清单**逐条裁定**——不重新表述、
不合并同类项、不省略"看起来不重要"的。

## 自检清单

- [ ] **核心模型已提炼**：五步法找出了作者自命名的框架，每个定义已回原文锁定
- [ ] **模型关系图已梳理**：层级/流程/支撑关系已画成文字版，放 skill 最前面
- [ ] `name` 是英文小写 slug，≤40 字符，仅含 `[a-z0-9-]`
- [ ] `description` 含触发词 + 使用场景 + 动词动作，无同名词歧义
- [ ] `description` **三段式**含 `⚠️不调用` 路由护栏；已过「边界段↔触发词反向一致性检查」（见下节）
- [ ] 内容**可操作/可调用**，不是空泛摘要
- [ ] **未编造**原书没有的引用/案例/数据（有疑义标"待核实"或附出处）
- [ ] **隐含模型已标注**（非原书命名的模型标"延伸解读"，不冒充作者原话）
- [ ] 译本术语已统一，关键外文词已标注原文
- [ ] 去噪完成（无序言/致谢/广告残留）
- [ ] 中文书用了合适模板（语录/心法类未硬套步骤型）
- [ ] 关键观点附了出处索引

## ⚠️ description ↔ 边界段反向一致性检查（v1.5.1 新增，高频 bug）

> 2026-08-31 CCPS 批1/2/3 实测：**边界段写了"不适合 X"，触发词却同时裸列 X** —— 边界说不要、触发词在招手。这比"没写边界"更隐蔽：写的人以为自己声明过了，路由却仍会把它拉起来。

**检查方法**：把边界段"不适合"清单里的每个关键词，拿去 description 触发词列表里**反向搜一遍**，有交集 = 矛盾：

| 情况 | 处理 |
|------|------|
| 该词在本 skill 确有合法场景（如 PHA 里的"要不要上 LOPA"、SIS 里的"LOPA 保护层判定"） | 保留触发词但**加限定语**区分场景，并在 ⚠️不调用段点名排除执行层场景 |
| 该词纯属执行层 / 属其他 skill（如"相容性"数据查询、"泄放尺寸计算"、"PFDavg 验算"） | **从触发词删除**，只在 ⚠️不调用段保留作路由目标 |

**推荐结构**：description 用三段式 —— `场景描述 + 触发词 + ⚠️不调用路由护栏`。只有触发词、没有护栏的 description，等于把路由决策全交给关键词匹配。

> **⚠️ 检查时两段独立，防假阳性（v1.7.0 新增，2026-08-31 批6 实测）**：初版脚本把 `⚠️不调用：` 段里的消歧词（如"F-N 曲线""风险等值线"用作路由目标）误判为触发词冲突——**触发词段是"本 skill 能做什么"，⚠️不调用段是"本 skill 不做什么 + 路由去哪"，两段的词天然会有重复**。检查时先按 `触发词：` 与 `⚠️不调用：` 切分两段，只把「⚠️不调用段列出的词」拿去「触发词段」搜，若触发词段该词**只出现在"不调用"语境**（如"F-N 曲线（→ 专业 QRA 软件）"）则不冲突；真正冲突是**同一裸词同时作为本 skill 的能力卖点与边界排除**。批5/批6 标准做法：`check_desc_batch5.py` / 参考脚本分离两段独立检查。

**一键检查**：

```bash
DESC=$(sed -n '4p' SKILL.md)   # 取 description 行
for w in LOPA 相容性 泄放 PFDavg 物性; do
  echo "$DESC" | grep -q "$w" && echo "⚠️ 冲突: $w"
done
```

## 触发词 ↔ 正文落点一致性检查（v1.15.0 新增，2026-09-11 实测）

> **触发词是"承诺清单"**：description 里写了什么能力，正文里就必须有对应的**可执行条目**。写了做不到的，用户按触发词调用只会拿到**空回答**。

2026-09-11 实证：某产出 description 写了 `%GRR 多少算合格`（贴近用户真实提问方式），回原文 grep **零命中**——该阈值属 AIAG MSA 口径，不是本书内容。**触发词越贴近用户口语，越容易写出资料里根本没有的承诺。**

三个一致性检查互补，各防一层：

| 检查 | 防的问题 | 位置 |
|------|---------|------|
| 触发词 ↔ 边界段 | **越界**——边界说不要、触发词在招手 | 本文档上一节 |
| 触发词 ↔ 正文落点 | **空诺**——承诺了能力，正文没有 | 本节 |
| 边界段 ↔ 下游 skill | **悬空**——指出去了，但没有那个 skill | 产出「应用边界」节 |

**做法**：把 description 触发词逐个拿去正文 grep，命中 0 的要么补正文依据、要么从触发词删除（并说明该需求该找谁）。

## 数量标准（通过/不通过信号）

| 检查项 | 通过 | 不通过 |
|--------|------|--------|
| 核心模型 | 3-7 个，各有来源证据 | <3 或 >10 |
| 方法论/清单 | 3-8 条，可操作 | <3 或全是泛泛原则 |
| 概念词汇表 | 5-25 个，有定义——**上限按主题复杂度定档**（2026-09-11 实测：通用统计类 19 / 25 个属正常，原「5-15」上限与实测不符） | 只列术语不给定义 |
| 应用边界 | 明确写适用范围和局限 | 只写优点不写局限 |
| 案例 | 至少 3 个，有书中支撑 | 无案例或案例不准确 |

## 反编造回查 MISS 处理规范（v1.7.0 新增，2026-08-31 批6 实测）

> 批6 实证：首轮断言回查 **3 个 MISS**，逐条回查原文后发现全部是**断言关键词写法与原文措辞不完全匹配**（如 "frequency of an incident is less well understood" 被拆成两半、大小写差异、换行断词），最终 20/20 全过。**MISS 不等于编造**，先诊断再下结论：

| MISS 原因 | 诊断法 | 处理 |
|-----------|--------|------|
| 断言关键词写法与原文措辞不一致（最常见） | 换同义词/核心子串/大小写不敏感重搜；原文可能跨行 | 修正断言写法后重搜，命中即算通过 |
| 原文确有该概念但用不同表述 | 搜概念核心词（如 probit 搜 "mean value of 5" 拆开搜 "5"） | 确认概念存在即算通过 |
| 原文真没有（真编造） | 回查失败且无任何同义表述 | 删除该断言/标注"延伸解读" |

**纪律**：MISS 后**先怀疑断言写法，再怀疑原文**——写断言时尽量贴近原文措辞（可先 grep 原文再写断言），减少假阴性；真编造零容忍。

## 验收器编写指引（v1.14.0 新增，2026-09-10 工程统计实战）

> 给已有产出做增补/回流时，本清单要落成**可跑的脚本**而不是靠肉眼。以下四条是写这类脚本时最容易犯的错。

### ① 自制检查规则的出错概率 > 被检查内容

09-10 实证：两轮共 48 项检查，**失败项 100% 来自检查器、0 项来自内容**。

**纪律**：看到 FAIL 的第一反应必须是 "**产物错了，还是检查器错了？**"——不能直接去改产物。判据：先把 FAIL 项单独拎出来手工复核一次（看原始数据），再决定改哪边。

### ② 判据要用真解析器，不要手写正则/关键词

09-10 实证：YAML 判据写"裸标量不得含 ASCII 引号"，**这个前提本身就是错的**（非行首的 `"` 在裸标量内合法）→ 报警一轮。

**做法**：
- 结构判定优先调真解析器——YAML 用 `yaml.safe_load()`、JSON 用 `json.loads()`、XML 用解析库，让它们**实跑一遍**而不是自己模拟语法规则
- 只有当解析器不覆盖时（如"行高是否够容纳换行文本"）才自写规则，且自写规则要**先用已知正确的样本试跑**确认不误报

### ③ 检查范围按语义限定，不要全文一把梭

09-10 实证两例：
- 统计"标记条目数"用 `str.count("◆")` → 得 10、期望 7——**多出的 3 个是概念表"出处"列的引用**。正确做法：只数**独占一行的标记**（`line.lstrip().startswith("◆")`）
- 核对交叉引用时把**缺陷表里"引号内引述的旧错误文字"**当成活引用报警（假警报）。正确做法：扫描前先剥离引述内容，只保留"改为「…」"这类修正后的目标

**纪律**：写到"统计 / 全文搜"类检查时，先问一句"**这个字符串还会出现在哪些非目标语境里？**"——命中场景多于一个就要限定范围（限定到行首 / 排除引用区 / 排除代码块）。

### ④ 验证时机：改完立即跑，别攒到最后；新规则先用真实数据自验

内容改完 → 立刻跑验收器 → 有 FAIL 当场辨因。攒到交付前再跑，会把"内容层返工"和"检查器层返工"混在一起，两轮都白跑。

**新增检查规则时，先拿真实产物空跑一遍再信它**——每加一条规则，立刻对**实际文件**（不是自造的构造样本）跑一次，确认它**不误报**。新规则的误报率往往高于被检查内容，且**只在真实数据上才暴露**：`[8b]` 标签匹配把引号内引述的旧错误文字当活引用、`os.path.islink()` 把 8/8 健康 junction 误报成实体目录、硬编码期望值过期造出一片假 FAIL——三条都是新规则自己错，且都只有真跑数据才发现。

### ⑤ 判据必须写明单位与口径依据（v1.15.0 新增，2026-09-11 实测）

三条实证同一个根因——**阈值写死时没写清"量什么、什么单位、以哪个状态为准"**：

| 实例 | 后果 |
|------|------|
| 体积红线写死 `55*1024 = 56,320`，而项目口径是十进制 KB（55 KB = 55,000 B） | 红线被**放宽 1,320 B**——超线文件显示合格 |
| 体积用"文本模式读取后重编码"计数 | CRLF 文件**每行少算 1 字节**（600 行 = 600 B）；方向是**漏报**，比误报更危险 |
| 压力类判据混用 Pa / kPa | 差 1,000 倍 |

**纪律**：写死任何阈值前，先写清 **量什么对象 / 用什么单位 / 以哪个文件状态为准**，并在代码里留一行注释说明该口径的**依据**（如"姊妹 skill 磁盘 54,385 B，文档记作 54.4KB → 故取十进制 KB"）。

**口径没写明的阈值，等价于没有阈值**——它只是在某一次运行里恰好对上了。
