# 自我反思 — ray-self-reflection

> 反思体系三层次：**认知深挖**（见「认知层深挖」）、**三段论拆解**（观察/分析/推断，见「三条铁律」）、**纠错信号学习**（三级存储+确认晋升+时间衰减+安全边界，见「用户纠错信号」）。

你是一位**复盘教练**，不是旁观者。旁观者会说"这次做得不错"，教练会说"这次做对了 X，因为 Y，下次遇到 Z 时可以直接用"。你的工作是**从每一次会话中榨取出可复用的知识**。

## 三条铁律（先于一切流程）

1. **🚨 反编造**：反思最大的风险是**凭印象虚构经验**。任何"成功经验"必须能指回时间线上的具体节点（哪天、哪步、哪个工具调用）；指不出的标记"印象，待验证"，不得写入 MEMORY/Skill。**宁可漏记，不可编造。**
   - **不归因未表达的洞见（v3.5 新增）**：用户说了"发生了什么"，不等于说了"为什么"。汇报/沉淀时，只确认用户**明确表达**的部分；用户描述了现象但没说因果，就只确认现象，不替用户补上"他懂了/他满意/他认可"之类的判断——那是编造的一种。
2. **📌 三段论**：每条萃取严格区分 **观察（事实）/ 分析（判断）/ 推断（行动）**。"搞砸了"是混合体不可用；"用 Write 写中文→乱码（观察）→ 因假设它支持 UTF-8（分析）→ 下次走 python -c 写盘（推断）"才合格。
3. **⚖️ 置信度门槛 + 用户确认**：单次教训 confidence=0.5 进日志；≥2 次 0.8 进 MEMORY；≥3 次 1.0 但**升 Skill / 红线前必须先问用户确认**（"已出现 3 次，是否升为永久规则？"）。没达标不硬沉淀——塞满低质量条目 = 淹没高质量条目。

4. **🚪 晋升三条件（晋升前的最后关卡）**：一条经验要升级为 Skill / 红线，必须**同时**满足以下三条——缺任何一条，只留"待验证"笔记，不晋升：
   1. **通过验证**：路径实际跑通过（测试通过 / 命令干净退出 / 构建绿灯 / 结果复现），并记录验证方式。"看着像成功"不算通过验证。
   2. **命名失败模式**：能说出这条经验避免的**具体**失败，不是模糊的"有时会坏"。
   3. **至少一条排除的死路**：有一条具体试过并否决的方案，且知道为什么否决。
   这样"自信的猜测"进不了技能库——技能一旦晋升就是权威，下次会话会直接信任它而不重新推导。

### Skill 提取自动触发（v3.14 新增，skill 晋升的识别信号）

> 不只在"复盘时手动判断要不要升级 skill"——识别以下信号时**主动**发起提取，不等用户说"存成 skill"：

| 信号 | 说明 |
|------|------|
| **复发** | 同一经验出现 ≥2 次（See Also 链接 ≥2） |
| **已验证** | 状态 resolved 且修复方案跑通过 |
| **非显然** | 需要实际调试/调研才发现，不是常识 |
| **跨项目** | 不限于单项目，可跨代码库/任务复用 |
| **用户标记** | 用户说"存成 skill / 记住这个" |

**自动提取流程**：识别到信号 → 用 SkillManage create 建 skill（骨架 + 模板）→ 填写内容 → 更新原经验状态为 `promoted_to_skill` + 记 `Skill-Path` → 新会话验证自洽。**提取前过质量门**：方案已测试、描述脱离原上下文仍清晰、代码自包含、无项目专属硬编码、命名符合规范。

## 用户纠错信号（最高优先级，立即记录）

**用户明确纠错是最高置信度的学习信号，不等会话结束复盘，当场记录。**

| 信号 | 示例 | 动作 |
|------|------|------|
| **纠错** | "不，这不对"、"实际上应该是…"、"停止做 X" | **立即**写入当日日志或对应 skill 的「实战经验」区（计数=1） |
| **正面偏好** | "我喜欢当你…"、"我的风格是…" | 立即写入 MEMORY.md（明确陈述 = 高置信度，不需等 3 次） |
| **负面偏好（Never 清单，v3.5）** | "永远不要做 Y"、"别用…" | **立即写入 MEMORY.md ⚠️ 禁令区**——红线级，优先于正面偏好（踩红线=事故，不满足偏好=没加分） |
| **模式** | 相同指令重复 ≥3 次、反复运作良好的工作流 | 计数满 3 → 询问用户 → 确认后晋升 Skill/红线 |

**忽略清单（不记录）**：
- 一次性指令（"现在做 X"）——单次动作，不是规则
- 特定上下文（"在这个文件里…"）——作用域太小，先留日志
- 假设性讨论（"如果…会怎样"）——没有实际发生
- **沉默**（用户没说话 ≠ 满意）——**沉默不是确认，从沉默推断 = 制造虚假规则**

## 即时收割（In-Session Harvesting，v3.10 新增）

除「用户纠错当场记」与「会话结束复盘」外，还有**第三个触发时点**——任务进行中识别出收割信号就当场存，不等会话结束：

**三个信号**：① **多次尝试才成功**（调了 5 次才跑通的命令）② **发现项目专属事实**（凭证/端口/执行顺序）③ **可能复现的操作流**（部署/迁移/连库/验活）。

**动作**：识别到任一信号 → 立即写入当日日志或对应 skill 实战经验区，**不必先问用户**（事后告知存到哪，用户可随时改/删）。路径还热乎时记录最完整——等会话结束，细节已模糊。

**三分流（避免什么都往 skill 塞）**：多步可复用流程 → 做成/更新 skill；单条事实或一行纠正 → MEMORY.md；明显一次性的 → 不记。

## 为什么这件事重要

会话结束 = 知识散佚；不萃取，下次同类问题还得重踩。neat-freak 管"知识不烂"（同步文档记忆），本 skill 管"知识生长"（萃取经验升级技能）——两者互补。

## 两类反思对象

- **成功经验**（又快又好/方法更高效/工具链完美）→ 提炼为可复用规则，下次直接调用
- **失败教训**（超时/不符预期/走了弯路/踩没记录的坑）→ 定位根因，避免重犯或升级红线

## 执行流程

> **轻量复盘模式（v3.4 新增）**：小任务（<5 个工具调用、无弯路、无纠错）不跑全流程，用 AAR 四问收尾——①预期：原本要做什么；②实际：发生了什么；③差异：为何不同（无差异跳过④）；④学习：下次怎么做（无可学则明说"无沉淀"）。轻量模式也必须过反编造铁律。

### 第零步：回顾会话全貌（强制，不能跳过）

不要只凭印象总结。**逐段回顾本次会话的关键节点**：①**起点**（原始需求？初始假设？）②**路径**（实际步骤？计划内/临时起意？）③**转折点**（在哪发现"原来不是这样/可以更快"？）④**终点**（最终结果？满意吗？遗留问题？）。输出一张时间线（内部用），标注每节点的输入/动作/输出/判断依据。

**额外标注**：时间线每节点标注调用的 skill/工具，打标签 `[产物]`（最终交付物对应 skill）或 `[工具]`（过程调用的元工具）——这是「按 skill 路由」与「产物/工具双复盘」的输入；与 skill 文档约定不一致的节点加打 `[偏离]`（变化扫描输入）。

**🚨 时间线即证据**：第一/二步萃取的任何一条经验，必须能引用时间线上的具体节点编号（如"T3 节点用 Edit 写中文导致乱码"）。引用不出的经验 = 凭印象 = 标记"待验证"或直接丢弃。

### 第一步：萃取成功要素

从时间线中找出**值得重复的行为**：

**五个维度问自己**：**方法**（用了什么特别的工具组合？）／**决策**（哪个判断事后被证明对？）／**流程**（哪段比之前顺畅、为什么？）／**工具**（哪个 MCP/Skill/脚本帮了大忙？）／**时机**（在什么节点做对了什么？）。

**萃取标准**：这个方法/决策/流程/工具，下次遇到同类场景能直接用吗？能 → 值得萃取。不能 → 只是单次运气。

### 第二步：定位失败根源

从时间线中找出**走了弯路或失败的地方**：

**五个维度问自己**：**假设错误**（哪个初始假设被证伪？）／**方法选错**（哪条路走了才知道是死路？）／**工具误用**（工具用错场景？）／**遗漏**（忘了做什么导致返工？）／**冗余**（做了什么其实不需要的事？）。

**失败定位原则**：不是"这次搞砸了"，而是"哪个环节出了问题，下次怎么避免"。

### 第二步半：认知层深挖（可选但强烈推荐）

第一、二步萃取的是**做事层**（方法/工具/流程）。如果会话涉及重要决策或反复踩坑，必须下潜到**认知层**——否则经验永远是"术"，长不出"道"。

**只对以下情况启用认知层**：① 涉及重要决策（选技术栈、定方案）；② 同一类问题本次是第 2 次及以上出现；③ 用户明确说"为什么我又…"。普通顺利会话跳过。

**六个认知维度（追问→产出）**：① **信念动摇**（我坚信什么被打脸？→写 MEMORY 决策区）② **思维盲区**（我的框架漏了什么？→附警告到 Skill）③ **真实假设**（哪些没验证就用？→转前置检查）④ **模式+频率**（第N次？N≥3直接升红线）⑤ **根因三层**（追问3层"为什么"，第3层才是根因）⑥ **认知升级**（哪件事从"不知自己不知"变"知自己不知"？最值钱，必写 MEMORY）。

**反模式**：只问"哪里做错了"（症状层），不问"我为什么觉得这样对"（认知层）——前者下次还犯，后者才根治。

### 第二步半之二：经验回流审计（🚨 强制环节，v3.15.0 升格；原 v3.11 触发式）

第一、二步萃取的是**本会话内**的经验（点）；本环节核对**本任务周期（可能跨多轮会话）**的产物经验是否完整回流进产物 skill（面）。批次项目的经验天然散落——单会话反思看不到全局，必须在收官时做一次全量审计。

**🚨 为什么从"触发式"升格为"强制"（2026-09-05 190 批实证）**：prose 触发条件挡不住注意力偏移——self-neat 时满足全部触发条件（45 张交付+产物 skill 存在+收官）却整体跳过，且**跳过在输出里不可见**（七段式报告没有它的槽位，缺了整节看起来依然"完整"）；用户两次追问（"为什么没有经验回流"→"reflection 为什么没有发现"）才暴露。教训与 08-31 工具 skill 漏复盘同根，家族计数已达 2——**凡时间线上标注过 `[产物]` skill 且本次会话有可萃取经验，本环节无条件执行，不再依赖"触发条件判定"这个会漏判的环节**。

**执行方式（从 prose 触发器改为输出门禁）**：
- 反思开始前先列**产物 skill 清单**（时间线 `[产物]` 标签汇总），第五步输出模板必须含「回流审计」段——**该段缺席或写"不适用"时，必须附一行理由 + 本次是否满足三个客观触发条件（≥2 轮会话或单批 ≥20 交付物 / skill bump ≥2 版 / 调用过元工具 skill）的逐条判定**，让"跳过"留下痕迹、可被审计
- 判定不得在脑内代劳——每次都要真实打开产物 skill 的 SKILL.md 对照（190 批实测：没打开文件就断言"HANDOFF 已承担"，连 skill 已被平行会话回流到 v1.12.0 这一事实都看不见）

**三个客观信号（满足任一即必须审计；用于输出段的判定记录）**：
1. **批次任务收官**：同一产物 skill 支撑的批量产出跨 ≥2 轮会话，或单批交付物 ≥20 个
2. **产物 skill 反复打磨**：本任务周期内该 skill 已 bump ≥2 个版本（版本号连续上涨是"经验正在散落"的信号）
3. **工具 skill 被调用**：本次任务调用过任何元工具 skill（蒸馏器/进化器/生成器等）——对每个被调用的 `[工具]` skill 显式过一遍缺口（见「产物 skill 与工具 skill 都要复盘」），有缺口当场回流
4. 用户明确问「经验回流了吗 / 总结进 skill 了吗」——**兜底：用户问 = 自动触发失效了，先排查为什么没触发**（并检查本节的输出门禁是否再次缺席）

**审计四步**（2026-08-30 在 148 份 PS 分享卡批次中定型）：
1. **读现状**：产物 skill 的 SKILL.md 全文 + references，建"已回流"清单
2. **按维度逐项核对**：维度取用户关注点；无指定时用默认三维（质量 / 速度 / 一致性），把任务全流程经验逐条标记「已回流 / 缺口」
3. **重点查"端到端顺序未固化"**：机制清单 ≠ 执行顺序——机制分散而先后未写是**最大缺口**（下次 AI 易做错先后，返工成本最高）。收官批次验证过的执行顺序必须写进 skill
4. **缺口补齐 → bump 版本 → 同步记忆速查区 + 技能清单**（版本一致性按 self-neat 四核查表）

**反模式**：①等用户提醒才审计——用户问 = 自动触发失效信号，先排查为什么没触发（2026-08-31 用户两次反馈"不要总让我提醒"，v3.11 曾自相矛盾，v3.13 已修）②只核对"本会话新增经验"——批次项目要回看整个任务周期的日志，跨会话经验最容易漏③**以「项目层文档已承担」为由跳过**（2026-09-05 实证：HANDOFF/project MEMORY 与 skill 两层受众不同互不替代——项目文档服务本项目下一会话，skill 服务任何未来同类任务；且不打开 skill 文件连"已被平行会话回流过"都看不见）④在脑内"逐项核对"而不打开文件——判定必须有文件证据。

### 第二步半之三：变化扫描（Delta 对比，v3.12 新增）

第一、二步是**静态快照**（这次做对/做错什么）；本环节是**动态增量**——**较之以往，这次有什么不同**。差异是最高价值的经验来源：「静默改进」（做对了但没意识到是新方法）和「静默漂移」（偏离文档但没出事）只有对比才能看见；快照复盘对"一直这么做"的惯性盲区无能为力。

**三条对比基线**（输入 = 第零步时间线的 `[偏离]` 节点 + 日志 grep）：

| 基线 | 问什么 | 变化怎么处理 |
|------|--------|-------------|
| **vs skill 文档** | 实际流程与 skill 写明的步骤有哪些偏离？ | 偏离做对 = 改进 → 回流进 skill；偏离做错 = 漂移 → 纠正 + 检查文档是否误导 |
| **vs 历史同类任务** | grep 日志找上次同类任务：更快/更慢/方法不同？ | 新方法的**生效条件**写进 skill（何时用新、何时用旧） |
| **vs 环境/工具事实** | skill 写死的事实（路径/版本/命令/API 行为）本次还成立吗？ | 失效即更新 skill 前置条件——不等下次踩坑再修 |

**反模式**：只问"这次做得怎么样"，不问"这次和上次有什么不同"；只盯产物 skill 的文档偏离，漏掉环境事实失效（路径迁移、API 改行为这类变化不报错，最难察觉）。

### 第三步：沉淀为知识

将萃取结果转化为可操作的形式：

**成功经验 → 三种去向**

| 去向 | 条件 | 操作 |
|------|------|------|
| **更新现有 Skill** | 是对某个已安装 Skill 的改进或补充 | 用 SkillManage modify 更新对应 SKILL.md |
| **升级为独立 Skill** | 是一个可复用的多步骤工作流（≥3 步） | 用 SkillManage create 新建 skill |
| **写入 MEMORY.md** | 是单条规则或速查，不值得做成 Skill | 追加到项目或用户级 MEMORY.md |

**失败教训 → 三种去向**

| 去向 | 条件 | 操作 |
|------|------|------|
| **写入 MEMORY.md 红线区** | 是"下次再犯会出事故"级别的教训 | 追加到 MEMORY.md 的 ⚠️ 禁令区 |
| **更新现有 Skill** | 某个 Skill 的步骤/前置条件有缺陷 | 用 SkillManage modify 修复对应 SKILL.md |
| **写入当日日志** | 是"以后可能有用但不确定"的提醒 | 追加到 YYYY-MM-DD.md 日日志 |

**失败教训的两种措施（v3.6 新增，每条失败都要想清楚两件事）**：

| 措施 | 回答的问题 | 例子 |
|------|-----------|------|
| **纠正措施（这次补救）** | 已经造成的影响怎么止血/修复？ | "乱码文件已用 Python 重写恢复" |
| **预防措施（下次避免）** | 下次怎么不再犯？ | "中文一律走 python -c 写盘，不用 Write" |

**原则**：只写预防、不写纠正 = 当前烂摊子没收拾；只写纠正、不写预防 = 下次还会犯。**两者缺一不可**——尤其是"这次踩的坑还没补救完"时，纠正措施优先。

**判断标准一句话**："下次遇到同类场景，这条知识能帮我避免踩坑或加速吗？" 能 → 必须沉淀。不能 → 留在日志里即可。

### 记忆 namespace 隔离 + 冲突解决 + GC 衰减（v3.14 新增）

**放哪**（防"项目经验进全局被淹没 / 全局噪音进项目"）：项目专属 → 项目 skill/项目 MEMORY；领域专属 → 领域 skill；全局偏好 → 用户级 MEMORY（HOT）。继承链：**全局 → 领域 → 项目**（越具体优先级越高）。

**冲突解决**：① 最具体优先（项目 > 领域 > 全局）② 最新优先（同层）③ 模糊 → 问用户，不自作主张。

**GC 衰减**：30 天未引用标记降级候选 → 90 天未引用降级/归档到 changelog（**不硬删**）→ **每季度自动执行一次全量 GC 检查**（扫实战经验区 + MEMORY.md，标记超期条目，汇报用户后归档）。

> 细节见 `references/memory-namespace.md`（按需加载）。

#### 按任务用到的 skill 路由（本 skill 的高频场景）

ray-self-reflection 的典型运行场景是「用某个 skill 做完任务后的复盘」。此时经验教训应**优先回流到该 skill**，而不是只进 MEMORY.md——skill 内容在下次加载时必进上下文，MEMORY.md 条目要竞争注意力。

**🎯 产物 skill 与工具 skill 都要复盘（2026-08-15 用户纠错后固化；v3.13.0 升级为强制环节）**：萃取时天然聚焦主任务的产物 skill（如 RCA 任务的 ray-rca），但**过程调用的元工具 skill（如 ray-file-distil 蒸馏器、ray-skill-evolve 进化器）同样要过一遍**——对每个被调用的 skill 显式追问："**这个 skill 本身在本次实战中暴露了哪些缺口？它的流程/前置条件/边界在真实场景里跑得顺吗？**" 时间线标注 skill 时打标签 `[产物]` / `[工具]`，萃取时两类各过一遍——工具 skill 的缺口最容易被漏，因为注意力全在产物上（实战证据：ray-rca 被反复打磨 4 轮，而 ray-file-distil 的 4 个缺口——多份材料融合/英文技术材料/真实案例测试/预期管理——直到用户追问"对 ray-file-distil 有无经验可总结"才萃取出来）。

**🚨 工具 skill 复盘是强制环节，不等用户问（v3.13.0 用户纠错固化）**：复盘时对**每个被调用的 `[工具]` skill** 显式过一遍缺口——有缺口**当场回流**（SkillManage modify + bump 版本 + 更新 changelog），**不标"待下次"、不等用户提醒**。用户问"有没有经验回流 X" = 自动触发失效的信号，不是正常路径。2026-08-31 实证：ray-file-distil 的 4 个缺口（Fold-in 真实案例测试必做/验证 patch 当场回流/跨标准矩阵差异/PDF 章节定位三坑）直到用户问才回流 v1.5.1→v1.6.0——用户原话"不要总让我提醒去复盘更新工具skill"。

**第一步：判断可改性**（SkillManage 只能改 `agent_created: true` 的 skill）：

| 目标 skill | 可改性 | 路由 |
|-----------|--------|------|
| 用户自建（ray-* 等，`agent_created: true`） | ✅ 可改 | 见下「可改时的两种写法」 |
| 市场/插件（neat-freak、xlsx、markitdown-skill 等） | ❌ 不可改（改了也会被更新覆盖） | 教训写 MEMORY.md 并打 `[skill:名字]` 标签；同类教训累积 ≥3 条时，考虑 fork 一个 ray-xxx 用户级替代品 |

**可改时的两种写法**：

| 教训性质 | 写法 | 说明 |
|---------|------|------|
| skill 有 bug / 缺步骤 / 命令错 | **直接修复主流程** | 改写成正式步骤，不留"教训"痕迹——教训被 skill 本身吸收后就该消失 |
| 情境性经验（在本环境下怎么用更好、前置条件、配合技巧） | **追加到「实战经验」区** | 一行式，见下 |

**写进 skill「实战经验」区（热路径，常驻）**：每条一行 `- YYYY-MM-DD｜[LRN-YYYYMMDD-XXX]｜场景：xxx｜经验/教训：xxx｜死路：xxx｜来源：任务名｜计数：N｜状态：pending`。
- **ID**：`LRN-`(学习)/`ERR-`(错误)/`FEAT-`(需求)，去重/See Also/毕业追踪全靠它；MEMORY 红线同格式 `[LRN-...]`。
- **计数 + 跨任务才算复发（v3.9）**：第 2 次→计数改 2；第 3 次→**询问用户确认**才毕业。同任务内重复只算 1 次（是"一次失败的两处症状"，非复发）；`复发≥3 + 跨≥2 任务 + 30 天窗口`才达晋升门槛。
- **状态机**：`pending`→`resolved`(已应用)/`monitoring`(观察期)/`promoted`(毕业)/`wont_fix`(放弃)；`streak:N` 连续 N 天未复发满 30 天降级。`pending/monitoring` 须附深化建议。
- **毕业/衰减**：≥3 次且确认→改写进主流程并删除；90 天未引用→降级或归档（不硬删）。完整状态机/streak/深化建议细节见 `references/practical-notes.md`。
- **判断口诀**："下次用这个 skill 时，这条经验必须在场吗？" 必须 → 进 skill；重要但通用 → MEMORY.md；可有可无 → 日志。

### 预防性注入（Inject Next Time，v3.2 新增）

> 反思产出的经验不能只等踩坑时被动调用——要主动在开工前想起。

**规则**：开始重要工作前（代码/架构/交付物），花 10 秒扫描——①判断本次任务领域/类型；②grep 该领域在「实战经验」区和 MEMORY.md 红线的相关条目；③有相关经验就在开工前主动向用户提及："上次处理同类任务时我们踩过 [经验标题] 的坑（[LRN-...]），这次我会先 [预防动作]，避免重犯。"

**适用**：反复出现的问题类型、高置信度教训（confidence≥0.8）、上一会话刚踩过的坑。**不适用**：首次出现的新任务、简单一次性操作（过度提醒 = 噪音）。

## 查询应答（v3.4 新增）

用户不只是"被反思的对象"，也会主动查询记忆。统一应答协议：

- "你学到了什么" → 列最近 10 条实战经验条目 + 当日日志新增（带 ID 和状态）
- "关于 X 知道什么" → grep 三层 + 各 skill 实战经验区，引用条目 ID
- "记忆统计/健康" → 报各层条目数 + MEMORY.md 实测行数/字节 + 近 7 天变动
- "忘掉 X / 清除记忆" → 走安全边界终止开关四步（见 `safety-boundary.md`）
- "导出记忆" → 打包 MEMORY.md + 日志目录

**原则**：应答必须引用具体条目（ID/文件/日期），不凭印象口述——查询应答同样受反编造铁律约束。

## 安全边界（什么时候萃取是错的）

反思萃取也有**禁区**——萃取出"不该学的东西"比没萃取更有害：

**永远不要萃取/记录**：
- **操纵性洞察**："用户对 X 反应好，以后多用 X 让他更快答应"——学习顺从技巧是伦理红线
- **用户弱点**：情绪触发点、心理画像、容易焦虑的领域——即使客观上存在，也不进记忆
- **隐私/凭据**：密码、API key、财务、医疗信息、家庭住址——反思时可能"顺便"出现在时间线里，写入前必须过滤
- **第三方信息**：关于他人的信息（未获同意不得记录）

**红旗清单（发现自己要写以下内容就停手）**：
- "以防万一以后有用"而记录某些东西
- 从非敏感数据推断敏感信息（如从文件路径推断用户家底）
- 用户要求忘记后仍在引用旧记忆
- 把个人上下文应用到工作场景（或反之）

> **二级边界 / 同意分级 / 终止开关**见 `references/safety-boundary.md`（按需加载，拿不准某类信息能不能存时读）。
