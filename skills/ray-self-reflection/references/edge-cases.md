# 特殊情况处理（按需加载）

> 从 SKILL.md 卸载（v3.10.0）。**何时读**：会话情况特殊、拿不准该不该反思或怎么处理时。

## 触发克制（何时不主动反思，v3.5 新增）

反思是手段不是目的，以下情况**不触发**（反思成本 > 收益，强行反思 = 打扰用户）：

| 情况 | 原因 |
|------|------|
| 纯信息查询 / 简单问答（无实质工作产出）| 没有可萃取的经验 |
| 会话 <3 轮 或 <5 分钟 | 工作量不足以支撑有效复盘 |
| 用户本会话已说"不用复盘 / 别反思 / 跳过" | 尊重用户，本会话不再主动触发 |
| 用户正处于连续任务流中（明显还有后续步骤）| 延后到任务收尾，不打断心流 |

**主动反思的前提**：有实质工作完成 + 有可萃取的经验/教训。宁可少反思一次，不硬凑一次。

## 六类特殊场景

- **会话很顺利，没什么可反思的**：检查是否有"隐性的成功"——比如某个默认行为恰好避开了坑，值得记录下来变成显式规则。但**沉默 ≠ 确认**：用户没抱怨不代表你做对了，隐形成功必须能指出"具体哪个行为避开了哪个坑"，指不出就不沉淀。
- **会话失败，用户不满意**：优先定位**可操作的改进点**，而不是泛泛说"下次注意"。每一条教训必须能回答"下次具体怎么做"。
- **发现之前记录的经验已经过时**：用 SkillManage modify 更新对应的 Skill 或 MEMORY.md，不要只新增不删旧。
- **连续多次会话踩了同一个坑**：说明之前的教训没有真正沉淀——这次必须升级为 Skill 或红线，不能只写日志。升级前先询问用户确认（见「实战经验」区约定）。
- **用户主动撤销某条规则**（"其实我改主意了"）：按撤销协议——① 将旧规则归档并加时间戳（保留历史）；② 记录撤销及原因；③ 新偏好作为候选重新计数，不直接继承旧置信度。
- **保守维护原则（heartbeat 哲学，v3.8 新增）**：周期维护的第一姿态是**不制造 churn**——大多数维护轮次应该"什么都不做"。整理是手段不是目的；没违规就不动。

  三条硬线：①绝不删除数据、清空文件、覆盖不确定的文本（宁可留冗余，不可误删）；②优先 append / 汇总 / 索引修正，而非整体重写；③配置审查的目的是**找违规**，不是找存在感——没违规就是"无变化"。
